# Phase 03: Code Review Report

**Reviewed:** 2026-09-28T12:00:02Z
**Depth:** standard
**Files Reviewed:** 32
**Status:** issues_found

## Summary

This phase (dedupe -> classify -> extract-CVEs -> rank -> group) is unusually well-defended: no `dangerouslySetInnerHTML`, no `eval`, no hardcoded secrets, no empty catch blocks, ReDoS-bounded regexes with adversarial-input tests (100k-200k char inputs asserted under 500ms), ID validation done twice independently before it ever becomes an `href` (extractCves + cveChips's anchored re-validation), ISO-date parse failures clamped instead of propagated, and union-find dedupe logic that is provably order-independent and covered by a wide edge-case test suite (transitive chains, ties, idempotency, non-mutation).

No BLOCKER-level defects were found — no injection vector, no auth bypass, no crash-causing null dereference reached the review. The findings below are correctness edge cases, an observability gap, and test-robustness concerns that should be addressed but do not block shipping this phase as-is.

## Warnings

### WR-01: `summary`'s `item.content` fallback is not HTML-stripped like `contentSnippet`, contradicting the module's own "already HTML-stripped" assumption

**File:** `src/lib/pipeline/normalize.ts:61`
**Issue:** `summary: truncateSummary((item.contentSnippet ?? item.content ?? "").trim())`. `rss-parser`'s `contentSnippet` is auto-generated by stripping HTML tags from the raw content, but `item.content` (the fallback used when `contentSnippet` is absent) is **not** stripped — it can contain raw markup (`<p>`, `<img>`, entity-encoded attributes, etc.). `ArticleCard.tsx`'s own doc comment states "`rss-parser` already delivers an HTML-stripped snippet" and relies on that invariant to justify rendering `article.summary` as a plain JSX text child with no further sanitization step. That assumption only holds for the `contentSnippet` branch, not the `item.content` fallback branch. This is not an XSS risk (JSX text nodes are always escaped by React, so worst case is literal tag text like `<p>...</p>` visible to the reader), but it is a real display-correctness defect: any feed item that populates `content` without a computable `contentSnippet` will render broken-looking raw markup on the front page, and no test exercises this fallback branch with actual markup (`normalize.test.ts` only tests the "both absent" case, not "content present with markup, contentSnippet absent").
**Fix:** Either strip tags from the `item.content` fallback before truncating (e.g., a small tag-stripping pass consistent with this codebase's "no new dependency" bias), or drop the fallback entirely and treat a missing `contentSnippet` the same as a missing summary (`""`), and add a test that exercises an item with `content` set but `contentSnippet` undefined.

### WR-02: CVE sequence-number regex caps at 7 digits, silently truncating (not rejecting) IDs with 8+ digit sequence numbers into a wrong, still-valid-looking CVE ID

**File:** `src/lib/pipeline/extractCves.ts:17`, `src/lib/cveChips.ts:20`
**Issue:** `CVE_PATTERN = /CVE-\d{4}-\d{4,7}/gi` and the anchored `CVE_ID_SHAPE = /^CVE-\d{4}-\d{4,7}$/` both cap the sequence number at 7 digits. The official CVE ID syntax (MITRE/CVE.org) has no upper bound on sequence-number length. If a feed ever mentions an ID with 8+ digits (e.g. `CVE-2026-123456789`), the regex greedily matches only the first 7 digits, producing a **different, syntactically-valid-looking ID** (`CVE-2026-1234567`) rather than failing to match. That truncated ID then passes `cveChips.ts`'s independent validation unchanged and is rendered as a clickable chip linking to `https://nvd.nist.gov/vuln/detail/CVE-2026-1234567` — a plausible-looking but incorrect/nonexistent NVD page, silently misleading a reader who trusts the chip. This is currently low-probability (real-world CVE sequence numbers are still well under 7 digits as of today) but is a genuine correctness gap with no test coverage for the 8+-digit case (the existing test only proves 4-digit and 7-digit numbers match, and that a 3-digit number is rejected — it does not prove an 8-digit number is rejected rather than truncated).
**Fix:** Add a trailing word boundary or an explicit "reject if followed by another digit" check, e.g. `/CVE-\d{4}-\d{4,7}(?!\d)/gi` (and the equivalent `(?!\d)` before the anchored `$` doesn't apply since `$` already forbids trailing digits in the anchored variant — but the *global* `CVE_PATTERN` used for extraction needs the negative lookahead so it doesn't stop mid-number). Add a regression test with a 9-digit sequence number asserting no ID (or no truncated ID) is extracted.

### WR-03: `getFrontPage`'s error path has zero logging — a total, sustained failure across all 13 sources is invisible to operators

**File:** `src/lib/pipeline/getFrontPage.ts:59-68`, `src/app/page.tsx:24-25`
**Issue:** `getFrontPage`'s outer `catch` swallows `err` into `{ status: "error", reason: ... }` with no `console.error`/logging call, and `page.tsx` discards the `reason` entirely, rendering the same quiet empty state as a genuinely quiet 24h window (an intentional D-03 UX decision). The result is that there is no code path anywhere in this phase that surfaces a getFrontPage-level failure to any operator-visible channel (server logs, error tracking, etc.). Given this app runs stateless on Vercel with no monitoring infrastructure described elsewhere in the reviewed files, a systemic bug (e.g. a change to `fanOut`/`filterLookback` that throws for every request) would present in production as an indefinitely "quiet news day" with no diagnostic trail.
**Fix:** Add a `console.error(err)` (or equivalent structured log) in `getFrontPage`'s catch block before returning the error variant, so Vercel's function logs retain the failure reason even though the rendered page stays quiet by design.

### WR-04: `test/productionPage.test.ts` detects "an article rendered" via an exact, attribute-order-sensitive string match, unlike the order-independent check the same file already uses for NVD anchors

**File:** `test/productionPage.test.ts:98`, `test/productionPage.test.ts:120`
**Issue:** `hasArticleAnchor = /target="_blank" rel="noopener noreferrer"/.test(body)` requires `target` and `rel` to appear adjacent and in that exact order in the emitted HTML. The same file's NVD-anchor test (lines 150-166) explicitly avoids this fragility by extracting each `<a>` tag first and then checking for `target="_blank"` and `rel="noopener noreferrer"` as independent substrings, tolerant of attribute order. The generic anchor check does not apply that same lesson: any future change to `ArticleCard.tsx`/`CveChips.tsx` JSX attribute order, or a React/Next.js version bump that changes attribute serialization order, would silently break `hasArticleAnchor` (and the section-count assertion at line 120 that depends on it) without any code-level regression, purely a test artifact.
**Fix:** Reuse the same tag-then-substring approach already written for the NVD-anchor check (extract `<a>` tags via `matchAll(/<a\b[^>]*>/g)`, then test each tag for both attributes independently) for `hasArticleAnchor` as well.

### WR-05: `frontpage.e2e.test.ts` makes unmocked live network calls to production third-party feeds with no timeout, retry, or offline-skip handling

**File:** `src/lib/pipeline/frontpage.e2e.test.ts:1-210`
**Issue:** Every test in this file calls `fetchSource`/`getFrontPage` against the real, live URLs in `SOURCES` (13 external domains) with no mocking, no network-failure fallback, and no explicit per-test timeout. `assert.equal(result.status, "ok", "expected fetchSource to succeed against the live feed")` and `assert.equal(result.status, "ok", "getFrontPage must never surface an error while at least one source is healthy")` will fail the whole suite if the sandbox/CI runner has no outbound network access (a common restriction in locked-down CI environments), if any one of the 13 upstream feeds is briefly down, or if a feed's markup changes shape. This is a deliberate design choice per the file's own comments ("Assertions are deliberately source-agnostic... End-to-end test driving the whole traced path against the live feeds"), but it is still a genuine CI-reliability risk worth flagging explicitly: a transient third-party outage becomes a build failure with no distinction from an actual regression.
**Fix:** At minimum, gate this file behind an explicit opt-in (e.g. an `E2E=1` env var check with an early return/skip when unset) so a standard `npm test` in a network-restricted CI environment doesn't fail on infrastructure it doesn't control, while still allowing it to run in environments (or a scheduled job) that do have egress.

## Info

### IN-01: CVE-ID shape is defined independently in two files with no shared constant

**File:** `src/lib/pipeline/extractCves.ts:17`, `src/lib/cveChips.ts:20`
**Issue:** `CVE_PATTERN` (global, extraction) and `CVE_ID_SHAPE` (anchored, validation) both hardcode the same `CVE-\d{4}-\d{4,7}` shape independently. The `cveChips.ts` comment explains this is intentional defense-in-depth (D-14) rather than an oversight, which is a reasonable security posture — but it does mean a future change to what counts as a valid CVE ID (e.g. fixing WR-02 above) must be applied in two places to stay consistent, and nothing enforces that at compile time.
**Fix:** No change required given the documented intent, but consider a comment cross-reference in both files pointing at each other (only `cveChips.ts` currently references `extractCves.ts`) so a future editor touching one pattern is prompted to check the other.

### IN-02: `dedupe.test.ts`'s "input array is not mutated" test cannot detect in-place mutation of an article's own fields

**File:** `src/lib/pipeline/dedupe.test.ts:237-245`
**Issue:** `const inputCopy = [...input];` is a shallow copy — `input[0]` and `inputCopy[0]` are the same object reference. `assert.deepEqual(input, inputCopy)` will pass even if `dedupe()` mutated a field on one of the `Article` objects in place, because both sides of the comparison see the same mutated object. The test only actually proves the *array* wasn't reordered/spliced, not that the *article objects* were left untouched, despite its name and stated intent. (Note: `dedupe.ts`'s current implementation does not mutate article objects, so there is no live bug today — this is a test-robustness gap that would fail to catch a future regression.)
**Fix:** Take a deep copy (e.g. `structuredClone(input)` or `input.map((a) => ({ ...a }))`) before calling `dedupe`, and compare against that deep copy instead of a shallow one.
