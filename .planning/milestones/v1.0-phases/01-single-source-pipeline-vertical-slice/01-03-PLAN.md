<objective>
Prove the branches real traffic never exercises. Krebs's own redirect is legitimate — same host, HTTPS — so production traffic only ever walks the *follow* path of the redirect guard; the *reject* path and the timeout path stay unproven until something deliberately misbehaves. This plan supplies that something: a hermetic local fixture, the negative-path tests it drives, the pure-transform edge tests, and the production-build HTTP checks that close out the caching and no-authentication criteria.

Purpose: ROADMAP Success Criterion 5 names redirect rejection and timeout abort as observable behaviours, and Success Criterion 4 names the caching window. Neither is verifiable by reading the code, and neither is verifiable under the dev server, because Next.js never caches pages in development. This plan is where those criteria stop being assertions and become tests.

Output: a green suite covering every negative branch of the pipeline, plus a production-build HTTP contract for the public page.
</objective>

## Flagged assumptions carried into execution

- **A1 (unresolved, from RESEARCH.md):** whether Krebs requires a browser-like `User-Agent` from Vercel's IP ranges specifically. Task 3's human-check on a preview deployment is the **only** point in this phase where that question can be answered — a local production build shares none of Vercel's IP reputation.
