than one security source in one recency-ordered list, **so that** I stop visiting each site
individually.

stability, the e2e test's hard-coded single-source assertions, the tier-colour map) is exercised
identically by 2 sources and by 13. Proving it on 2 catches an architectural dead-end after one
commit instead of after the full source list is wired.

wired as source #2, and the complete 6-colour tier palette.

## T-01-05 Re-evaluation (required by this phase's security contribution)

Phase 1 accepted T-01-05 (`01-SECURITY.md`, AR-01) on the basis of "single hardcoded HTTPS
source", and explicitly named this phase's fan-out as where the residual DNS-rebinding risk
becomes material. Decision for Phase 2: **re-accept, severity low, with the following updated
reasoning.** A private-IP-range denylist on redirect targets is deliberately NOT implemented,
because analysis shows it would add no coverage:

1. **The literal-IP vector is already closed by a stronger check.** `fetchWithValidatedRedirect`
   requires `target.protocol === "https:"` AND `target.host === originalHost` (exact string
   equality, port included). Every configured `url` is a public HTTPS hostname, so a redirect
   target that is an IP literal, `localhost`, or any private-range address fails host equality
   before any denylist would be consulted. A denylist on the target *string* is strictly
   subsumed by exact-host-equality — it would be dead code.
2. **The only residual vector is a configured hostname resolving to a private IP**, i.e. true
   DNS rebinding against one of 13 hostnames that are fixed at build time in tracked source
   (`src/lib/config/sources.ts`) and belong to major, publicly-registered security publishers.
   An attacker must first compromise DNS for one of them.
3. **The impact ceiling is low even on success.** The request carries no credential (no cookie,
   no `Authorization` header, no bearer token — the app has no auth surface at all, UI-06). The
   response body is only ever size-capped, XML-parsed, and rendered as escaped text. There is no
   write path, no internal service reachable from Vercel's egress that this app knows about, and
   no secret to exfiltrate in the request. A successful rebind yields a read of a body Havadis
   then publishes as public text.
4. **Implementing resolved-IP validation would build on an unverified assumption.**
   `02-RESEARCH.md` Open Question #2 and Assumption A2 record that Node's global `fetch`
   (undici) does not hand application code the resolved IP before connecting, and that the
   custom-dispatcher / DNS-lookup-override API surface needed was NOT verified this session.
   Coding against it now is exactly the "stall on an unverified technical assumption" risk A2
   names.
5. **ASVS L1 with `security_block_on: high` permits acceptance at this severity.** The residual
   is low (low likelihood × low impact), well under the blocking threshold.

**What underwrites the acceptance:** Plan 02-02 adds `src/lib/config/sources.test.ts`, a
hermetic test asserting every configured `url` is `https:` with a non-IP-literal, non-local
hostname. That converts premise (1) from a reviewer's reading of the code into an automated
invariant, so the acceptance cannot silently rot if a future source is added carelessly.

**Revisit trigger:** if a future phase introduces a user-supplied or runtime-configurable source
URL, or a credentialed outbound request, premises (1) and (3) both break and this must be
re-opened as `mitigate`.
